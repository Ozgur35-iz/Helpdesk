# CLAUDE.md (server)

Server-specific conventions. See the repo-root `CLAUDE.md` for the cross-cutting auth architecture and overall project context.

**Roles** (`admin` | `agent`) live on `User.role` in `server/prisma/schema.prisma`, exposed to better-auth via `user.additionalFields.role` in `auth.ts` with `input: false` — meaning role can never be set through the public sign-up/update API, only via direct DB/adapter access. Sign-up is disabled entirely (`emailAndPassword.disableSignUp: true`); the only ways to create a user are `server/prisma/seed.ts` (single admin, via `auth.$context`) and the admin-only `POST /api/users` route (`server/src/routes/users.ts`), which creates agents the same way (`internalAdapter.createUser` + `ctx.password.hash` + `linkAccount`).

**Request body validation** uses `parseBody` (`server/src/lib/validate.ts`) — a shared helper wrapping Zod's `.safeParse`: on failure it writes the `400 { error: <first issue message> }` response itself and returns `undefined`, so route handlers just do `const data = parseBody(someSchema, req.body, res); if (!data) return;`. Define the Zod schema at the top of the route file (see `server/src/routes/users.ts`, `server/src/routes/webhooks.ts`) and use `parseBody` for every new route that validates a request body — don't hand-roll `safeParse`/`400` again.

**Generated Prisma client is committed to git.** `schema.prisma` outputs to `server/generated/prisma` (not `node_modules`), and that generated directory is tracked in version control rather than gitignored — after any schema change, run `db:generate` (and `db:migrate` for a schema change) and commit the regenerated output along with the migration.

**Env vars** are consumed via `process.env` directly in server code (Bun auto-loads `.env`); the Prisma CLI config (`server/prisma.config.ts`) additionally does an explicit `import "dotenv/config"` since it runs outside Bun's runtime. Known vars: `DATABASE_URL`, `PORT` (server, default 3001), `CLIENT_ORIGIN` (better-auth trusted origin, default `http://localhost:5173`), `ADMIN_EMAIL`/`ADMIN_PASSWORD` (seed script only), `INBOUND_EMAIL_SECRET` (shared-secret token for the inbound-email webhook), `GOOGLE_GENERATIVE_AI_API_KEY` (used by `@ai-sdk/google` for the AI endpoints — `POST /api/tickets/:id/polish-reply` and `POST /api/tickets/:id/summarize` — both on model `gemini-flash-latest`, a Google-maintained alias so the routes don't break as specific Gemini versions get deprecated).

**`POST /api/tickets/:id/summarize`** builds a prompt from the ticket body plus all replies (oldest first, each tagged with its author's name) and returns `{ text }`, a 2-4 sentence summary. It's stateless — nothing is persisted, so calling it repeatedly (e.g. after new replies come in) just regenerates the summary; the client re-renders whatever came back last.

**Inbound email → ticket webhook** (`POST /api/webhooks/inbound-email`, `server/src/routes/webhooks.ts`) is the only route that isn't session-authenticated — it's a machine-to-machine endpoint meant to be called by an email provider, so it checks an `x-webhook-secret` header against `INBOUND_EMAIL_SECRET` instead of `auth.api.getSession`. It accepts a generic `{from, senderName, subject, body, messageId?}` JSON body (not shaped after any specific provider like Postmark/Mailgun — see `CLAUDE.md` for why the stack diverges from `tech-stack.md`'s planned provider integration) and creates a `Ticket` row with `status: "open"` and `category: null`. `messageId`, if provided, is stored as `externalMessageId` (unique) so retried webhook deliveries don't create duplicate tickets.

**Automatic classification** runs as a background job on a **pg-boss** queue (`server/src/queue.ts`). The webhook handler enqueues `{ ticketId }` on the `ticket-classification` queue (`boss.send`, wrapped in try/catch so an enqueue failure never fails the webhook) and immediately responds with `category: null` still on the just-created ticket. `startQueue()` (called from `src/index.ts` on boot) starts pg-boss, creates the queue with `retryLimit: 3, retryBackoff: true`, and registers the worker; the worker calls `classifyTicketById` (`server/src/lib/classify.ts`), which re-fetches the ticket and asks `gemini-flash-latest` to pick one of `categoryValues` (`server/src/lib/categories.ts`, shared with `tickets.ts`'s `PATCH /:id/category`), then updates the row in place. An API/transport error throws out of the worker so pg-boss retries (3x, exponential backoff); a well-formed but unrecognized model response is logged via `console.error` and treated as terminal (no throw, no retry), leaving `category: null` for an agent to set manually. There's still no UI indicator that classification is in flight — a ticket just quietly gains a category a few seconds after creation.

pg-boss keeps its own tables in a dedicated **`pgboss` schema** (separate from Prisma's `public`), created/migrated automatically on `boss.start()` — no Prisma migration and no change to `db:test:setup` is involved. It reuses `DATABASE_URL`.
