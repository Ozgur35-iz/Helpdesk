# CLAUDE.md (server)

Server-specific conventions. See the repo-root `CLAUDE.md` for the cross-cutting auth architecture and overall project context.

**Roles** (`admin` | `agent`) live on `User.role` in `server/prisma/schema.prisma`, exposed to better-auth via `user.additionalFields.role` in `auth.ts` with `input: false` — meaning role can never be set through the public sign-up/update API, only via direct DB/adapter access. Sign-up is disabled entirely (`emailAndPassword.disableSignUp: true`); the only ways to create a user are `server/prisma/seed.ts` (single admin, via `auth.$context`) and the admin-only `POST /api/users` route (`server/src/routes/users.ts`), which creates agents the same way (`internalAdapter.createUser` + `ctx.password.hash` + `linkAccount`).

**Request body validation** uses `parseBody` (`server/src/lib/validate.ts`) — a shared helper wrapping Zod's `.safeParse`: on failure it writes the `400 { error: <first issue message> }` response itself and returns `undefined`, so route handlers just do `const data = parseBody(someSchema, req.body, res); if (!data) return;`. Define the Zod schema at the top of the route file (see `server/src/routes/users.ts`, `server/src/routes/webhooks.ts`) and use `parseBody` for every new route that validates a request body — don't hand-roll `safeParse`/`400` again.

**Generated Prisma client is committed to git.** `schema.prisma` outputs to `server/generated/prisma` (not `node_modules`), and that generated directory is tracked in version control rather than gitignored — after any schema change, run `db:generate` (and `db:migrate` for a schema change) and commit the regenerated output along with the migration.

**Env vars** are consumed via `process.env` directly in server code (Bun auto-loads `.env`); the Prisma CLI config (`server/prisma.config.ts`) additionally does an explicit `import "dotenv/config"` since it runs outside Bun's runtime. Known vars: `DATABASE_URL`, `PORT` (server, default 3001), `CLIENT_ORIGIN` (better-auth trusted origin, default `http://localhost:5173`), `ADMIN_EMAIL`/`ADMIN_PASSWORD` (seed script only), `INBOUND_EMAIL_SECRET` (shared-secret token for the inbound-email webhook), `GOOGLE_GENERATIVE_AI_API_KEY` (used by `@ai-sdk/google` for every AI feature — `POST /api/tickets/:id/polish-reply`, `POST /api/tickets/:id/summarize`, the background classification job, and the background KB auto-resolve job — all via the shared `src/lib/ai.ts`, which pins the model to `gemini-flash-lite-latest` — a Google-maintained alias, and the *lite* one because the plain `gemini-flash-latest` alias is frequently `503` "high demand" on the free tier — and exports `aiMaxRetries` (1) so a bad spell fails fast instead of stacking three ~60s attempts); `SENTRY_DSN` (error-reporting DSN for the HTTP server and worker process — empty/unset makes the Sentry SDK run as a disabled no-op client, so it's safe to leave blank).

**Error logging** goes through `@sentry/node`. `Sentry.init()` lives in `src/instrument.ts`, preloaded via `--import ./src/instrument.ts` in the `dev`/`start`/`worker` scripts (Sentry's recommended ESM pattern — init must run before express/http are imported anywhere). `src/lib/sentry.ts` just re-exports the `Sentry` namespace for `captureException` calls elsewhere. This is error-capture only — `tracesSampleRate: 0`, no tracing/profiling integrations — keyed off `SENTRY_DSN`. Coverage: `Sentry.setupExpressErrorHandler(app)` in `index.ts` catches route errors; `uncaughtException`/`unhandledRejection` handlers in both `index.ts` and `worker.ts`; `boss.on("error", ...)` in `queue/index.ts` for pg-boss's own errors; `queue/classification.ts`'s `boss.work` handler captures-then-rethrows so pg-boss's retry semantics (`retryLimit: 3, retryBackoff: true`) are unaffected; and `lib/auto-resolve.ts`'s catch block captures directly since it intentionally never rethrows.

**`disableInstrumentationWarnings: true`** is set in `instrument.ts` because Bun doesn't implement Node's `module.register` loader-hook API that `import-in-the-middle` needs for auto-instrumenting express/http — confirmed this isn't an import-order bug in this codebase (the "express is not instrumented" warning persists even on a direct `bun --import ./src/instrument.ts src/index.ts` run). That only costs automatic spans/breadcrumbs for those libraries, which don't matter with tracing disabled — manual `captureException` calls and `setupExpressErrorHandler` work fine regardless.

**`POST /api/tickets/:id/summarize`** builds a prompt from the ticket body plus all replies (oldest first, each tagged with its author's name) and returns `{ text }`, a 2-4 sentence summary. It's stateless — nothing is persisted, so calling it repeatedly (e.g. after new replies come in) just regenerates the summary; the client re-renders whatever came back last.

**Inbound email → ticket webhook** (`POST /api/webhooks/inbound-email`, `server/src/routes/webhooks.ts`) is the only route that isn't session-authenticated — it's a machine-to-machine endpoint meant to be called by an email provider, so it checks an `x-webhook-secret` header against `INBOUND_EMAIL_SECRET` instead of `auth.api.getSession`. It accepts a generic `{from, senderName, subject, body, messageId?}` JSON body (not shaped after any specific provider like Postmark/Mailgun — see `CLAUDE.md` for why the stack diverges from `docs/planning/tech-stack.md`'s planned provider integration) and creates a `Ticket` row with `status: "new"` and `category: null`, then enqueues both the classification and the KB auto-resolve jobs. `messageId`, if provided, is stored as `externalMessageId` (unique) so retried webhook deliveries don't create duplicate tickets.

**pg-boss job queues** live under `server/src/queue/`: `index.ts` owns the shared `boss` connection (`connectQueue()`, `stopQueue()`), and one module per queue sits next to it — `classification.ts` and `auto-resolve.ts`. Each queue module exports a `setup*Queue()` (connect + `createQueue`, for the producer), an `enqueue*(ticketId)` wrapper over `boss.send`, and a `work*Queue()` (setup + register the `boss.work` handler, for the worker).

**Automatic classification** runs as a background job on the `ticket-classification` queue, split across two processes:

- **HTTP server** (`src/index.ts`, runs under `bun --watch`) calls `setupClassificationQueue()` + `setupAutoResolveQueue()` — `boss.start()` + `createQueue(..., { retryLimit: 3, retryBackoff: true })` for each. The webhook enqueues via `enqueueClassification` / `enqueueAutoResolve` (wrapped in try/catch so an enqueue failure never fails the webhook) and responds immediately with `category: null` still on the ticket. No job handler is registered here.
- **Worker** (`src/worker.ts`, runs under plain `bun`, **no `--watch`**) calls `workClassificationQueue()` + `workAutoResolveQueue()`, which register `boss.work(...)` → `classifyTicketById` (`src/lib/classify.ts`) / `autoResolveTicketById` (`src/lib/auto-resolve.ts`). Classification re-fetches the ticket, asks Gemini (`src/lib/ai.ts`) to pick one of `categoryValues` (`src/lib/categories.ts`, shared with `tickets.ts`'s `PATCH /:id/category`), and updates the row in place. `SIGINT`/`SIGTERM` trigger `stopQueue()` (`boss.stop({ graceful: true, timeout: 30_000 })`) so an active job drains instead of being orphaned.

Why the split: a worker living in the `--watch` process gets killed on every file save, orphaning its active job in `active` state until `expireInSeconds` (900s) before pg-boss retries. Keeping it separate means HTTP reloads don't touch in-flight jobs. **Cost: the worker does NOT hot-reload — after editing `worker.ts`, anything under `queue/`, `lib/classify.ts`, or `lib/auto-resolve.ts` you must restart the dev stack.** `bun run dev` (root) launches client + HTTP server + worker together via `concurrently -k`; `bun --filter server worker` runs just the worker.

Failure handling: an API/transport error throws out of the worker → pg-boss retries (3×, exponential backoff). The SDK retry is capped at `aiMaxRetries` (`src/lib/ai.ts`) so pg-boss owns the real backoff rather than the SDK blocking a worker slot for minutes during a Gemini 503. A well-formed but unrecognized model response is logged via `console.error` and treated as terminal (no throw, no retry), leaving `category: null` for an agent to set manually. No UI indicator that classification is in flight.

pg-boss keeps its own tables in a dedicated **`pgboss` schema** (separate from Prisma's `public`), created/migrated automatically on `boss.start()` — no Prisma migration and no change to `db:test:setup` is involved. It reuses `DATABASE_URL`. Note the e2e test server (`test:server`) runs only the HTTP process, not the worker, so e2e-created tickets are enqueued but never processed — they stay at `status: "new"` (and `category: null`) forever. That's fine for the current specs (they only assert on the webhook response), but a future ticket-list e2e must account for `new` tickets being hidden.

**Automatic KB auto-resolution** runs on a second pg-boss queue (`ticket-auto-resolve`), handled by the same worker process. On arrival a ticket is `status: "new"` (hidden from the list). The job (`src/lib/auto-resolve.ts` → `autoResolveTicketById`) re-fetches the ticket, bails unless it's still `"new"` (idempotent for redelivered jobs / an agent who already grabbed it), flips it to `"processing"`, then asks Gemini (`src/lib/ai.ts`) — via `generateObject` with a `{ canResolve, reply, reason }` Zod schema — whether the support knowledge base (`server/knowledge-base.md`, read once and cached) fully answers it with no escalation-rule hit. `canResolve` → `status: "resolved"` + the drafted answer saved to `Ticket.aiResolutionReply`; otherwise → `status: "open"`. **Unlike classification, this handler never throws**: any error (Gemini failure, bad KB read) is logged and the ticket falls back to `"open"` so it can't get wedged invisibly in `"processing"`. The ticket list (`GET /api/tickets`, `src/routes/tickets.ts`) filters out `new`/`processing`; agents can't set or filter those statuses (`agentStatusValues`). Ticket statuses are still bare strings (no DB enum) — the full set is `new | processing | open | pending | resolved | closed`.

**Dashboard metrics.** `GET /api/metrics` (`src/routes/metrics.ts`, session-gated but any role — it's team-wide ops data, not admin-only) returns `{ totalTickets, openTickets, aiResolvedTickets, aiResolvedPercent, avgResolutionSeconds, ticketsPerDay }` for `client/src/pages/DashboardPage.tsx` (the `/` landing page). `ticketsPerDay` is a dense 30-element `{ date: "YYYY-MM-DD", count }[]` (oldest first, zero-filled) built from a `GROUP BY ("createdAt" AT TIME ZONE 'UTC')::date` raw query — days are UTC — and drives a hand-rolled CSS bar chart (no charting lib). `aiResolvedTickets` = tickets with a non-null `aiResolutionReply` (the only marker of an AI resolution); `aiResolvedPercent` is over *all* tickets. Average resolution time comes from `Ticket.resolvedAt`, a nullable column set the first time a ticket enters `resolved`/`closed` and cleared on reopen — written in `PATCH /:id/status` (`routes/tickets.ts`, diffs old vs new status) and in `lib/auto-resolve.ts`'s `canResolve` branch. `resolved -> closed` keeps the original timestamp. The avg is a `prisma.$queryRaw` (`AVG(EXTRACT(EPOCH FROM ...))`) over rows with a non-null `resolvedAt`; the `add_ticket_resolved_at` migration best-effort-backfilled pre-existing terminal tickets from `updatedAt`.
